### Coordination — ask the network to do work

The Intent → Proposal → Commitment → authorize → Result → Receipt loop, served by ln-coordination-gateway in front of a coordination core and a real three-node provider fleet. Authentication is a signed envelope carried in `x-ln-signed-request` (or, for the four operations whose body is itself the envelope, the body). There is no anonymous read: `session_id` is derived from content a third party can compute, so an unauthenticated read path would hand any stranger another party's Result and Receipt. The full schemas are in the OpenAPI document; this table is the index.

| `GET /version` | <Status level="implemented" /> | The contract version the gateway enforces and its own build version. Check this before blaming a signature: a client built against a different contract major fails as `signature_invalid`, which does not mention versions at all. |

### Compute App — the first application on the coordination API

A working application, not a demo shim: it reaches the platform over `https://libertynet.ai/coordination` and no private path, so what works here is exactly what works for anyone else. It holds **no requester key** — every mutating call carries the browser's already-signed envelope verbatim, and reads carry the browser's signed read credentials in `x-lnc-read-credentials`. That is why a session belongs to the browser that opened it and this service cannot read it on your behalf. `GET /` is the six-page browser UI, which signs with WebCrypto and keeps the key in the tab's memory only — reloading the page is a new identity.
