## The one rule

<Warning>
**Never describe something as more finished than it is.**

Not in a page, not in a code comment, not in an example, not in a commit message. If a
capability is not built, say so. If an endpoint returns placeholder zeros, say so next to
the zeros.

Every other rule here is a preference. This one is the point of the project.
</Warning>

├── examples/                  # Runnable examples

## Run everything

```bash
node tools/check-all.mjs
```

Twelve suites: the status generator, four honesty checks, the site renderer, every example
(really executed), the golden-question eval, both SDKs, the scaffolder and the MCP server.
It must pass before a PR merges.

```bash
node tools/check-all.mjs --live   # adds the live-network checks
node examples/run-all.mjs         # every example, including the networked ones
node tools/sync-status.mjs        # regenerate after editing the capability matrix
```

## Changing a capability's status

<Steps>
  <Step title="Ship the behaviour first">
    A badge changes in the same commit as the behaviour, never before it.
  </Step>
  <Step title="Edit api-spec/status.json">
    The single source, and now genuinely authoritative rather than merely agreed-with.
  </Step>
  <Step title="Regenerate">
    ```bash
    node tools/sync-status.mjs
    ```
    This rewrites the OpenAPI `x-ln-status` values, both SDK capability maps and the docs
    table. CI runs `--check` and fails if you hand-edit any of them — the same discipline as
    `gofmt -l`.
  </Step>
  <Step title="Write the prose yourself">
    Deliberately **not** generated. A capability moving to `implemented` needs a human to
    say what it does; a machine inventing that paragraph would manufacture exactly the
    confidence this project exists to avoid.
  </Step>
</Steps>

## Adding an example

The bar: **it must run, it must be honest, and it must teach one thing well.**

```bash
mkdir examples/my-example
# write it, then declare it in examples/manifest.json:
#   the command to run, and what its output must contain
node examples/run-all.mjs my-example        # must actually run and match
node tools/check-examples.mjs               # must pass
```

The manifest is what makes "done" unambiguous. The runner spawns your example, waits for it
and matches its real output — "it compiled" is not the bar, because examples rot silently.

**Assert the failures too.** The most valuable checks in the suite are the ones that require
things to go wrong correctly: a crossed DID/key pair must exit 1, a forged identity must get
401, a replayed signature must not verify. A suite that only checks happy paths would let
identity verification break without anyone noticing.

Checked automatically:

- No hard-coded secrets.
- Nothing that moves value — LibertyNet has none, so no example can demonstrate one.
- Identity verification present, with no escape hatch.
- Unbuilt capabilities throw rather than returning mock data.

And by review: every `→` output comment must have been produced by running the code.

## Writing documentation

<AccordionGroup>
  <Accordion title="Concepts and reference are separate, deliberately">
    `/concepts/` teaches a model. `/reference/` is a dictionary you look things up in.
    Mixing them produces pages that are too long to skim and too shallow to learn from.
  </Accordion>

  <Accordion title="Show the real output">
    Run the code, paste what it printed. Invented output is the most common way
    documentation becomes false, because nothing ever re-checks it.
  </Accordion>

  <Accordion title="Warn where people actually get hurt">
    The two that cost the most time on this network:
    `status: "active"` not meaning online, and DID string comparison splitting one node into
    two. Both get a `<Warning>` wherever they are relevant.
  </Accordion>

  <Accordion title="Both languages, or neither">
    TypeScript and Python examples in a `<CodeGroup>`. A page that shows only one silently
    tells half the readers this is not for them.
  </Accordion>

  <Accordion title="Preview it">
    ```bash
    cd docs-site && npx mint dev
    ```
  </Accordion>
</AccordionGroup>

## Lanes

This repository classifies changes by risk. For `dev-portal/`:

| Change | Lane |
|---|---|
| Docs, examples, SDKs, CLI, dashboard, MCP server | **Green** — normal review |
| `api-spec/status.json` | **Green**, but reviewed carefully — it drives every claim |
| Anything under `frozen/`, `.github/`, or runtime trust-root paths | **Red** — needs David's approval |

Nothing in `dev-portal/` touches money, security-critical protocol code, or frozen
specifications. If a change to this directory ever needs to, that is a signal the change is
in the wrong place.

## Pull requests

- One concern per PR.
- All tests green, including the honesty checks.
- If you changed a capability's real behaviour, `status.json` changes in the same PR.
- Say plainly what you did **not** do — an incomplete change with an honest note is far more
  useful than one that appears finished.
